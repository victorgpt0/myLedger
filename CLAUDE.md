# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

MyLedger is a single-module Android app (Kotlin, Jetpack Compose, Hilt, Room, WorkManager, DataStore) that builds a personal ledger by parsing financial SMS messages (currently Safaricom M-PESA) from the device inbox. Play package (`applicationId`): `com.waystar.myLedger` — permanent, case-sensitive; debug builds add `.debug`. Code package (`namespace`) stays `com.finance.myledger`; don't "fix" the mismatch. minSdk 24, compile/target SDK 36, JVM target 11. Dependency versions live in `gradle/libs.versions.toml`.

Release process, signing, Play forms and update priorities: `docs/release/PLAY_RELEASE.md`. Privacy policy: `site/privacy/index.html`, published to GitHub Pages (https://victorgpt0.github.io/myLedger/privacy/) by `.github/workflows/pages.yml` on pushes to `main`; the app links to it via `ui/common/Links.kt`.

App icon (adaptive foreground/background, outline-only themed layer, legacy mipmaps, Play Store PNG, SVG master; artwork traced from the `uglycash.webp` reference) is generated by `python3 tools/icon/generate_app_icon.py` (needs Pillow). Edit the script and re-run; don't hand-edit `ic_launcher_*.xml` or the mipmap webps.

## Commands

```bash
./gradlew assembleDebug                 # build debug APK
./gradlew installDebug                  # install on connected device/emulator
./gradlew testDebugUnitTest             # all JVM unit tests (incl. Robolectric)
./gradlew testDebugUnitTest --tests "com.finance.myledger.data.parser.MpesaParserTest"           # one class
./gradlew testDebugUnitTest --tests "com.finance.myledger.data.parser.MpesaParserTest.someTest"  # one method
./gradlew lint                          # Android lint
./gradlew bundleRelease                 # Play bundle (R8 on; signed if keystore.properties / MYLEDGER_* env vars exist)
./gradlew connectedAndroidTest          # instrumented tests (device required)
```

Unit tests use JUnit4 + Truth + kotlinx-coroutines-test. Repository tests run on Robolectric with an in-memory Room DB (`unitTests.isIncludeAndroidResources = true` is required for this). `app/src/test/resources/robolectric.properties` pins `sdk=35` because Robolectric 4.14.x can't run the app's targetSdk 36.

M-PESA body timestamps have minute precision, so same-minute transactions tie. The repository resolves ties via the balance chain in `domain/balance/BalanceChainResolver` — both the latest balance and the ordering of transaction lists (DAO sorts `timestamp DESC, rowid DESC`; the resolver reorders tied runs). Don't rely on `ORDER BY timestamp` alone.

## Architecture

Clean-architecture layering inside one module: `domain/` (pure Kotlin ports, models, use cases), `data/` (Android/Room/DataStore implementations), `ui/` (Compose screens + Hilt ViewModels), `di/` (Hilt modules binding domain ports to data impls).

- **Domain ports** — `TransactionRepository`, `SmsParser`, `SmsInboxReader`, `SmsPermissionChecker` (`domain/sms/SmsPorts.kt`), `SyncCursorStore`. ViewModels and use cases depend only on these; bindings are in `di/RepositoryModule.kt`. Known exception: `ParseAndStoreSmsUseCase` depends on `data.parser.ParserRegistry` directly.
- **Separate domain vs persistence models** — `domain/model/Transaction` vs `data/local/TransactionEntity`, converted in `data/mapper/TransactionMappers.kt`. Keep Room annotations out of domain.

### SMS ingestion pipeline

All three entry points funnel into `ParseAndStoreSmsUseCase` → `ParserRegistry.parse()` → `TransactionRepository.insert()`:

1. **Live**: `SmsReceiver` (SMS_RECEIVED broadcast, `goAsync()` + coroutine; joins multipart PDUs per sender).
2. **Full backfill**: `SmsBackfillWorker` (HiltWorker, unique work `sms_backfill`, enqueued from `DashboardViewModel` — automatically when the DB is empty, or via "Scan again") → `BackfillSmsUseCase` reads the entire inbox and reports progress.
3. **Incremental sync** (pull-to-refresh on Dashboard/Transactions): `SyncTransactionsUseCase` reads only SMS newer than the DataStore cursor (`SyncPreferences` / `SyncCursorStore`). Both backfill and sync advance the cursor.

**SMS access is restricted to known financial senders** (Play SMS policy + spoofing protection): each `SmsParser` declares `senderIds`; `SmsContentReader` filters the inbox query by them, `SmsReceiver` drops other senders, and `MpesaParser.matches()` checks the sender ID only (never the body — a look-alike text from a phone number must not become a transaction). Any new SMS source must declare its sender IDs. Anything that changes what SMS is read, stored or sent off-device must also update the disclosure in `SmsPermissionScreen`, the privacy policy, and the Play declaration/Data safety answers in `docs/release/`. Backups are disabled (`allowBackup=false` + exclude-all extraction rules) because the DB holds SMS text.

`DashboardViewModel` auto-starts the full backfill once per process when SMS access is granted and the DB is empty (first run, or after a destructive migration left the sync cursor ahead of the data).

Unmatched messages are silently dropped. Dedupe relies on the transaction `id` being the provider's reference code (e.g. M-PESA receipt) as Room primary key with `OnConflictStrategy.IGNORE`, so re-scanning is safe.

### Parsers and classification

- **Adding a new SMS source**: implement `domain.sms.SmsParser` in `data/parser/`, then add a `@Binds @IntoSet` method in `RepositoryModule`. `ParserRegistry` receives the multibound `Set` and uses the first parser whose `matches()` returns true — no other changes needed.
- `MpesaParser` is a list of (regex, extractor) pairs, one per message shape, with a real sample SMS documented above each pattern (send, receive, paybill/till, withdrawal, airtime, cash deposit, dividend, reversal). Add new shapes to that list **and bump `MpesaParser.version`**: `CheckParserUpgradeUseCase` then triggers one full re-import, because the incremental sync cursor has already passed messages older versions dropped (re-import is safe: inserts dedupe on id). Fees come from "Transaction cost, Ksh X" when present.
- **Reversals**: a `TransactionKind.REVERSAL` row carries `reversesId` (the cancelled transaction's code). Every aggregate query must include the `COUNTED` condition from `TransactionDao.kt` (excludes reversal rows and the rows they reverse); Kotlin-side aggregation must use `observeCountedInRange`. Lists and the balance use all rows.
- Counterparty strings are stored as written; group/display them through `domain/classifier/CounterpartyName` (strips masked/full phone numbers, "for account …", leading years, extra spaces) — never `GROUP BY counterparty` in SQL.
- `SelfTransferDetector` reclassifies known wallet counterparties (M-Shwari, KCB M-PESA, Fuliza, Hustler Fund, etc.) as `TransactionType.TRANSFER`.
- `CategoryClassifier` (domain) is a keyword heuristic mapping counterparty/body to `Category`.

### Persistence and analytics

- `AppDatabase` (version 4, `exportSchema = false`). Changing `TransactionEntity` means bumping the version **and** adding a migration in `data/local/Migrations.kt` (append it to `Migrations.ALL`, which `DatabaseModule` registers); `fallbackToDestructiveMigration()` only covers versions without one. `MigrationsTest` builds a real old-version DB and opens it with Room, which validates the schema — extend it for new migrations. Migrations that backfill from `rawMessage` must mirror the parser's pattern logic.
- Enums are stored as strings via `Converters`; DAO SQL compares against enum names (e.g. `type != 'TRANSFER'`).
- **Income/expense aggregates must exclude `TRANSFER`** so self-wallet movements aren't counted as spend/income; transfers have their own totals.
- `TransactionKind` (send / paybill / till / withdrawal / airtime / received) is set by the parser per message shape and drives the fee breakdown; it's separate from `TransactionType` (income / expense / transfer).
- SQL date grouping must use `strftime(..., 'unixepoch', 'localtime')` — plain `'unixepoch'` is UTC and shifts 00:00–02:59 EAT into the previous day/month. Kotlin-side calendar math (`domain/insights/PeriodMath`) uses the device default zone to match.
- Aggregations (category totals, monthly trend, day-of-week, top counterparties, fees) are SQL queries in `TransactionDao` returning row types defined in `TransactionEntity.kt`, exposed as `Flow`s through the repository and `Observe*UseCase`s, filtered by `DateRangeBounds` (from the `DateRange` sealed class / `ui/common/DateRangeSelector`).

### UI

Single `MainActivity` hosts `MyLedgerNavHost` and `ui/update/InAppUpdateController` (Play In-App Updates — the only update path Play allows; no-op for sideloaded/debug installs; mode chosen by pure `domain/update/UpdatePolicy`): bottom-nav destinations Dashboard, Time Analytics, Merchant Analytics; Transactions is pushed from the Dashboard (bottom bar hidden). Each screen follows `XScreen` / `XUiState` / `XViewModel` (`@HiltViewModel`) with screen-specific composables in a `components/` subfolder. UI refreshes reactively from Room Flows — sync actions don't need to push results to the UI manually. `SmsPermissionScreen` gates on READ_SMS/RECEIVE_SMS.
